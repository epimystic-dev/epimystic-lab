### `mcptoolcheck` -- static linter for MCP tool-descriptor files

Two independent 2026 signals converged on the same surface - the
server-side tool-advertisement surface each MCP server exposes via its
`tools/list` handshake - and together they establish a current unmet
need the lab's hygiene-linter family can serve directly.

1. **arXiv 2607.05744** (Rashidi, 2026-07-07): *"Unicode TAG-Block
   Concealment of Tool-Metadata Payloads in the Model Context Protocol:
   An Approval-View Fidelity Gap Across Three Independent Server
   Implementations"*. The paper names the fault class precisely:
   Plane 14 Tag characters (U+E0000-U+E007F), bidi overrides,
   zero-width characters, and private-use codepoints render as nothing
   in approval dialogs but reach the model tokenizer. 8/8 attack
   techniques delivered payloads across three independent MCP server
   implementations; 4/8 evaded string-matching sanitizers. The paper
   terms this an *approval-view fidelity gap* - the rendered approval
   view and the bytes delivered to the model do not have to match,
   and the protocol does not require them to.

2. **github.com/Paraphern/rugsnare** (HN 49945978, submitted
   2026-10-04 - the morning of this scan): the authors diffed every
   release pair of the four reference `@modelcontextprotocol/server-*`
   servers and found 140 silent changes across 66 release pairs
   (35% silent-change prevalence). The breakdown: 43 BREAKING
   `inputSchema` schema flips, 28 ANNOTATION flips (`readOnlyHint`
   / `destructiveHint` toggled), 7 COSMETIC description rewordings,
   37 tools / prompts / resources added post-approval, 24 removed.
   The report concludes: *"Not one was announced in a changelog."*
   The filesystem reference server (`2025.8.21 -> 2025.11.25`)
   simultaneously modified all 14 of its tool contracts in a single
   unannounced release.

The two signals land on the same trust surface - the tool-descriptor
object the server advertises. The host approves it once; neither the
paper's invisible-byte concealment nor the field report's silent drift
is observable from the record of that approval. The lab already
publishes `mcpservercheck` for the client-side *registration* surface
(how the server is installed / started / connected); the server-side
*advertisement* surface was uncovered. `mcptoolcheck` closes that gap.

The linter flags twelve shape defects across invisible-character
concealment (five classes: Plane 14 Tags, bidi overrides, zero-width,
C0/C1 controls, private-use codepoints; MTC-001 through MTC-005),
name-field hygiene (MTC-011, the higher-trust variant of the same
character-class attack), missing version/hash pin (MTC-006, the
silent-change detection surface the field report calls out as
universally absent), annotation-flip inconsistency (MTC-007, a
`readOnlyHint=true` on a `delete`/`write`/`update`-named tool, or a
`destructiveHint=true` on a `read`/`list`/`get`-named tool),
missing annotations (MTC-008), permissive or absent `inputSchema`
(MTC-009), cross-script homoglyph words (MTC-010), and length
anomalies (MTC-012, INFO).

5 HIGH / 6 MEDIUM / 1 INFO. 126 tests pass under
`python -m unittest discover -s tests`. Independent implementation,
not affiliated with or endorsed by the authors of the paper or of
the field report.

### Why one, not three

Three secondary candidates (WebMCP tool-surface poisoning linter for
the browser-integrated surface; intent-governed tool authorization
shape linter from arXiv 2606.22916; untrusted-tool-feedback input
schema linter from arXiv 2605.17453) are standing-watch candidates.
Each is a distinct surface, but each would need either a less-mature
schema (WebMCP), a more-complex intent-certificate shape (IGAC), or
a runtime data path (feedback). The lab's bar is "concrete, current
problem, world-class for its size, fully tested, this run."
`mcptoolcheck` cleared it; the three secondaries did not.

1. **arXiv 2607.05744** -- Rashidi, *"Unicode TAG-Block Concealment of
   Tool-Metadata Payloads in the Model Context Protocol: An
   Approval-View Fidelity Gap Across Three Independent Server
   Implementations"* (2026-07-07).
   https://arxiv.org/abs/2607.05744
   *Why this matters:* names the invisible-byte attack family on the
   MCP tool-advertisement surface, cross-validated against three
   independent server implementations; the formal basis for MTC-001
   through MTC-005 and MTC-011 in this week's build.

2. **github.com/Paraphern/rugsnare** -- field diff of 66 release pairs
   of the four reference `@modelcontextprotocol/server-*` servers,
   140 silent changes documented (HN 49945978, 2026-10-04).
   https://github.com/Paraphern/rugsnare
   *Why this matters:* the direct field evidence that the silent-
   change / annotation-flip pattern is live in production reference
   servers, not a theoretical risk; the empirical basis for MTC-006
   through MTC-009 in this week's build.

3. **arXiv 2606.06387** -- *"WebMCP Tool Surface Poisoning: Runtime
   Manipulation Attacks on LLM Agents"* (2026-06-04). Distinct from
   MCP: it names "Tool Hijacking" (abort/race-condition-based tool
   substitution) and "Tool Framing" (metadata manipulation of name /
   description / `readOnlyHint` / `inputSchema`) on the browser-
   integrated protocol.
   https://arxiv.org/abs/2606.06387
   *Why this matters:* a parallel surface to MCP; the framing-attack
   taxonomy is sibling to the fault class `mcptoolcheck` targets, and
   is a candidate for a sibling WebMCP linter in a future cycle.

4. **arXiv 2606.22916** -- *"Intent-Governed Tool Authorization for AI
   Agents"* (2026-06-22). Proposes `IGAC`: short-lived intent
   certificates narrowing the statically authorized tool manifest
   per-request; a dynamic-authorization framework rather than a
   shape primitive.
   https://arxiv.org/abs/2606.22916
   *Why this matters:* orthogonal to shape-linting; worth a sibling
   shape linter against the intent-certificate manifest once the
   schema stabilises.

5. **arXiv 2606.20922** -- *"Think Twice Before You Act: Protecting
   LLM Agents Against Tool Description Poisoning via Isolated
   Planning"*. Defense framework by isolated-planning quarantine.
   https://arxiv.org/pdf/2606.20922
   *Why this matters:* adjacent defense; shares the fault class
   `mcptoolcheck` catches at the file-shape surface. A runtime
   companion rather than a static replacement.

6. **arXiv 2605.17453** -- *"Trust No Tool: Evaluating and Defending
   LLM Agents under Untrusted Tool Feedback"*.
   https://arxiv.org/pdf/2605.17453
   *Why this matters:* names the untrusted-feedback input surface

   linter in a later cycle.

7. **arXiv 2607.21835** -- *"ToolGuardian: Declarative Security for AI

   https://arxiv.org/pdf/2607.21835
   *Why this matters:* declarative-security approach to the

8. **HN 49945978** -- "We diffed all 66 release pairs of the official

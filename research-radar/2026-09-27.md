### `approvchainlint` -- static linter for agent-tool approval configuration files

The direct motivation is arXiv 2609.28586 (Zhang et al., "Agent Approval
Laundering: Transitive Effects Beyond the Approved Invocation",
submitted 2026-09-23). The paper's central claim is that an approval
record binds a human decision to a *command or tool call*, but the
workflow that call activates can exercise transitive effects across six
effect classes (subprocess, network, filesystem-write, eval,
persistent-state, external-hook) that the record does not disclose.
The paper proves an information-limit result: identical policy-visible
fields can require different effect-specific decisions, so no
record-only policy can guarantee closure over the transitive workflow.

Two independent HN threads from the same week reinforce that the
fault class is not just formal - it is being weaponised as a UX
shortcut in the field:

1. **HN 49852101 -- "AI: Who Still Uses Permissions?"** documents
   user frustration with approval prompts that do not persist. The
   comment thread lays out the exact pressure that produces
   sticky / auto-approve / remember-approval defaults.

2. **HN 49830471 -- a "Show HN" for a tooling gateway that manages
   coding-agent approvals on the user's behalf.** A middleware layer
   that pre-approves tool calls against user-authored allowlists
   before the underlying agent is prompted. Correct as a productivity
   tool; also the exact laundering shape the paper's abstract names.

Given (a) the formal result that record-only policies cannot certify
closure, and (b) the field pressure toward sticky / auto-approve
patterns, a static linter over the config files that grant those
approvals is the correct pre-flight primitive: it cannot certify
safety, but it can name specific shapes that hide transitive effects
from the approval record - and so is the smallest useful defence.

`approvchainlint` reads a coding-agent `settings.json` with a
`permissions` block, an MCP `mcp.json` file with `mcpServers`, or a
generic agent-tool descriptor with a `tools` or `approvals` list, and
reports twelve shape defects on a 5 HIGH / 4 MEDIUM / 3 INFO split:

- **AC-001..005 (HIGH)**: wildcard-scoped subprocess / shell / eval
  approval; sticky / auto-approved / unbounded-TTL approval;
  approval scope broader than the tool's declared surface; delegator
  tool declaring child tools without a child-approval binding;
  network-capable tool with no host allowlist.
- **AC-006..009 (MEDIUM)**: approval entry is a bare tool name with
  no argument scope; read-only-labeled tool declares write / exec /
  network capabilities (mislabeled surface); duplicate approval keys
  with divergent policy fields; post-approval install-hook capability
  without its own gate.
- **AC-010..012 (INFO)**: delegator tool has no audit / trace /
  record-effects field; tool has an approval-shape field but declares
  no explicit effect class; pre-approved HIGH-effect tool listed at
  session start.

The rule set follows the family shape - verdict rollup, deterministic
exit codes, `--json` for CI, `--strict` / `--include-info` /
`--disable RULE_ID` per-repo overrides, exactly as in `mcpservercheck`,
`sarifcheck`, `nbshape`, and `pjhookcheck`.

174 tests: package-surface invariants (7), shared-contract CI
invariants (3), type / verdict / severity invariants, offset-to-
line-col across LF / negative / overflow, `find_key` with from-offset
and BOM strip via the `\ufeff` escape constant so no raw BOM byte
appears in source, JSON loading, snippet truncation and newline
flattening, latin-1 fallback, max-bytes truncation, rule-registry
invariants (count == 12, id uniqueness, canonical AC-NNN, non-empty
descriptions, valid severities, 5 / 4 / 3 HIGH / MEDIUM / INFO split,
disabled-suppresses, `run_all` matches registry), per-rule positive-
and-negative discrimination across all twelve rules, scanner tests
(direct-file kept, directory walk finds candidate files, deterministic
sort, max-files cap, missing path ignored, extra-glob, default-globs
constant, healthy zero findings, invalid-json error, missing-file
error, empty scan_paths, cross-file findings), verdict-and-exit-code
tests (no-files unknown, no-files-strict unhealthy, error forces
unhealthy, high wins, medium needs-attention, info hidden healthy,
info include-info needs-attention, info strict unhealthy, no findings
healthy, exit-code mapping 0 / 1 / 2 / 0 across all four verdicts),
text-and-JSON report tests (findings on stdout, summary on stderr,
info hidden by default, info shown with `--include-info`, errors
listed, JSON parseable, JSON deterministic across two renders, JSON
info hidden by default, JSON info shown with `--include-info`, JSON
errors field), CLI tests (`--version`, `--list-rules` covers every
AC-NNN, missing-path rc 2, unknown-rule rc 2, healthy rc 0, weak
rc 2, --disable flips verdict, `--json` flag, `--include-info` shows
AC-012, info hidden by default, directory walk with cross-file
findings, `--strict` on empty dir rc 2, `--max-files 0` collapses to
unknown, `--help` rc 0 and contains `approvchainlint`), end-to-end
fixture tests (weak fires every rule, weak has findings in every
severity, healthy fires nothing, sort is stable across two runs, JSON
round-trip determinism), and `python -m approvchainlint` subprocess
tests validating `--version`, `--list-rules`, and healthy exit-zero.

Dogfood: running `approvchainlint examples/weak_config.json
--include-info` yields verdict=unhealthy, exit 2, findings across
every one of the twelve rules. The same tool on
`examples/healthy_config.json` yields verdict=healthy, exit 0,
zero findings, under both default and `--strict --include-info`.

The lab's hygiene-linter family now covers file-content hygiene
(`envcheck`, `jsonlcheck`, `jwtcheck`), eval-stream hygiene
(`jsonldiff`, `jsonlsample`), install-manifest hygiene (`reqcheck`,
`licensechain`), contribution-policy hygiene (`aicontribcheck`), agent-

(`mcpservercheck`), security-scan-output hygiene (`sarifcheck`),

lifecycle-hook hygiene (`pjhookcheck`). `approvchainlint` adds the

files that describe what will be started or installed;
`approvchainlint` scans the file that describes what will be
*approved* at the tool-call boundary once those things are running.
Three orthogonal surfaces of the same root-cause class ("author-
supplied or third-party command runs on consumer's machine or
account under a policy that names too little").

## Method note

The artifact is an independent implementation built from the public
abstract of arXiv 2609.28586 and from standard tool-config schema
documentation (the coding-agent `permissions` block convention, the
Model Context Protocol `mcp.json` shape, generic agent-tool
descriptor conventions). No reference implementation of an
approval-chain linter was read, vendored, or mirrored. Not affiliated
with nor endorsed by the authors of arXiv 2609.28586 or by any tool
vendor, registry, or research group. Offline and stdlib-only: it
reads a JSON config, reports shapes, executes nothing it reads, and
opens no network connection.

As always, a linter reports shapes. It cannot detect an attack, and a
clean run is not a safety certificate. The paper's own information-
limit result is the ceiling: a policy-visible field set cannot
guarantee closure over the transitive workflow.

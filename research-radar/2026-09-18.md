An out-of-cycle digest. Where the weekly radar scans one modality deeply,
this entry is the product of six independent scans run in parallel and then
cross-examined: arXiv `cs.CR` and `cs.SE` (export API, submittedDate

Every candidate that came out of those scans was then put to three
adversarial reviewers - one checking that the problem is real and current,
one checking that it is buildable offline against the standard library

Ten candidates survived all three. Two were built.

## What we chose to build, and why

**Two artifacts**, holding the standing quality-over-quantity bar. Both read
plain JSON, both are stdlib-only, and both address a failure that is silent
by construction - the defect does not announce itself, it just quietly
removes a safeguard the team believes is in place.

### `sarifcheck` -- static linter for SARIF 2.1.0 result files

SARIF is the OASIS-standard interchange format that security scanners emit
and that code-scanning platforms ingest. The failure mode that motivated
this tool is that a SARIF file can be *simultaneously* well-formed JSON and
unusable: it can exceed a documented ingestion ceiling and be truncated, it
can carry absolute filesystem paths that never map back to repository files
so every finding lands on no line of code, it can reference rule metadata
that is not in the file, and it can omit the fingerprints that let a
platform deduplicate an alert across re-uploads.

Each of those produces the same user-visible outcome: the scan ran, the
upload was accepted, and the findings are not where anyone will look for
them. A green pipeline is indistinguishable from a working one.

The ingestion limits are published as fixed numbers - 20 runs per file,
25,000 results per run, 25,000 rules per run, 1,000 locations per result,
10,000 thread-flow locations - and the platform maintains a dedicated
troubleshooting page for exceeding them, which is itself evidence that the
failure is common rather than theoretical. The absolute-path defect has a
matching upstream fix in a maintained scanner whose SARIF URIs stayed
absolute when the path crossed a symlink, and the dangling rule-reference
defect has a matching upstream issue in a maintained linter emitting an
invalid `ruleIndex`.

`sarifcheck` reads the file a platform is about to ingest and reports those
shapes before the upload rather than after.

### `nbcheck` -- reproducibility and hygiene linter for notebook JSON

Computational notebooks are the standard medium for shared analysis and the
standard medium for irreproducible analysis. The notebook file format
records, per cell, the order in which cells were actually executed, and that
record is the evidence: when execution counts are out of order, duplicated,
or attached to outputs from a kernel session the file no longer describes,
the notebook cannot be re-run to the state it claims to show.

The literature on this is unusually concrete. An automated-modernization
study reports that roughly a quarter of 12,106 machine-learning notebooks
from a large public competition platform remain reproducible today. A
containerization study of 443 scholarly notebooks resolved two-thirds of
dependency failures and still found more than half showing low output
fidelity. A quality study of notebooks from a major journal's publications
executed 19 and reproduced 2, naming tangled state changes as a recurring
cause.

The second half of the tool is disclosure rather than reproducibility.
Notebook outputs are committed to the repository along with the source, and
those outputs routinely carry machine-local absolute paths that name a user
account, and cell source routinely carries credential-shaped literals bound
to names like `api_key` or `token`. A notebook is a file that leaks by
default, because the thing you commit includes the thing you ran.

`nbcheck` reads the notebook JSON and reports both classes: the execution
record that does not support the claim, and the payload that should not have
been committed.

## What was rejected, and why

Restraint is the gate, so the rejections matter as much as the picks.

- **PEP 751 `pylock.toml` linting** scored well and was genuinely tempting -
  the format is newly standardized, three installers now write it, and
  hashes are not enforced on install. It was rejected on a hard constraint:
  the standard-library TOML parser arrives in Python 3.11, and this lab's
  tools are tested from Python 3.10. Shipping it would have meant either
  hand-rolling a TOML parser or silently dropping a supported interpreter.
  The surface stays on the list for when the floor moves.
- **Vulnerability-suppression linting** (`osv-scanner.toml`, `.trivyignore`)
  was rejected for the same interpreter reason on its primary surface.
- **CI workflow linting** was rejected twice over: the surface is YAML,
  which the standard library cannot parse, and a mature, maintained static
  analyser already covers it well. Duplicating a good tool is not a
  contribution.
- **Notebook-adjacent determinism linting of training scripts** was rejected
  as too diffuse - the rules collapsed into heuristics over arbitrary Python
  rather than decidable checks over a specified format.

## Method note

Both artifacts are independent implementations built from specification text
and published findings only. No reference implementation of either tool was
read. Neither is affiliated with nor endorsed by the authors of any cited
work. Both are offline and stdlib-only: they read a file and report shapes,
they execute nothing they read, and they open no network connection.

As always, a linter reports shapes. It cannot detect an attack, and a clean
run is not a safety certificate.
